
  ho riscontrato il seguente bug che una volta non c'era, evidentemente è stato da me introdotto come regressione
  durante uno dei vari avanzamenti di versione del progetto @project\vForth18_DOES . Il caso è così descritto: se da
  ZX BASIC apro uno stream in output verso un file tramite p.es. OPEN#13,"o>out.txt" poi una volta avviato l'ambiente
  Forth devo essere in grado di usare la sequenza  13 SELECT 4 LIST  per dirottare su file l'output che attraverso
  EMIT  normalmente andrebbe verso lo stream #2 (video).
  Tornando poi al basic, avviene la ClOSE#13 che chiude il file out.txt, è possibile esaminarne il contenuto corretto.
  Il bug emerge quando, anziché lanciare  13 SELECT 4 LIST  lancio  13 SELECT WORDS  per il fatto che il file non contiene 
  informazioni sensate, solo sporco (vedi attuale conenuto @out.txt come esempio).
  Di più, durante l'esecuzione di WORDS il sistema sembra appeso e solo la pressione di BREAK consente di interrompere 
  l'esecuzione stessa di  WORDS.
  Non dipende nemmeno dal fatto di inziare con uno schermo vuoto CLS ed evitare lo scroll, in quanto anche la 
  sequenza  13 SELECT  1 100 INDEX   produce un out.txt perfettamente sano.
  L'anomalia è quindi circostritta alla definizione di WORD e/o con l'interazione verso lo stream. 
  Sono abbastanza certo che con la versione 1.7 di vForth questo non accadeva.
  Ti chiedo di effettuare una diagnosi esaminando le varie differenze di versione sotto @projects\vforth_DOES 
  per provare a risolvere l'anomalia.
